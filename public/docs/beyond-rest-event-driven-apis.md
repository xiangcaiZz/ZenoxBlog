# 超越 REST：现代应用的事件驱动 API

REST 作为 Web API 的通用语言已有二十年。但随着应用变得越来越交互化和实时化，请求-响应模式的局限性逐渐显现。

## REST 力不从心时

REST 对 CRUD 来说非常优美。你有一个资源，想读取或修改它——`GET /users/42` 或 `PATCH /orders/17` 完全合理。

但现代应用有不适配这种模式的需求：

- **实时更新**——仪表盘需要实时刷新，而非每 30 秒轮询一次。
- **长时间运行的操作**——报告生成需要几分钟，而非几毫秒。
- **多客户端同步**——一份文档被五人同时编辑。

在这些场景下，强行套用请求-响应模式会创建出脆弱、絮叨、低效的系统。

## 替代方案

### Server-Sent Events（SSE）

最简单的选择。服务器通过长连接 HTTP 推送事件。适合单向数据流——仪表盘、通知、实时信息流。

**优点：** 简单、自动重连、通过大多数代理。
**缺点：** 仅单向、每个域名有连接数限制。

### WebSocket

通过单个 TCP 连接实现全双工通信。当双方都需要主动发送消息时的正确选择。

**优点：** 双向、每条消息开销低。
**缺点：** 基础设施更复杂、需要处理重连逻辑。

### 消息队列（NATS、Kafka、Redis Streams）

对于后端到后端的通信，消息队列完全解耦生产者与消费者。

**优点：** 极高的可扩展性、持久化、回放能力。
**缺点：** 运维复杂度、最终一致性。

## 混合方案

最好的系统为每个场景选择合适的工具：

- **REST** 用于 CRUD 和符合资源语义的操作。
- **SSE** 用于向客户端推送状态变更。
- **WebSocket** 用于协作或双向功能。
- **消息队列** 用于异步后端处理。

关键洞察在于这些并非竞争者——它们是互补的原语。成熟的 API 设计会在合适的地方使用所有这些，而非只用一个。
